# 备份与恢复

Jant 有三种不同的恢复工具，它们解决的是不同的问题：

| 需求                       | 使用这个                                         |
| -------------------------- | ------------------------------------------------ |
| 把内容迁移到另一个站点     | `site export` 和 `site import`                   |
| 按原样恢复内部 ID 和存储键 | `site snapshot export` 和 `site snapshot import` |
| 应对生产环境数据丢失       | 真正的数据库备份，加上真正的媒体备份             |

如果你只记得一条规则，那就记住这条：

**一个完整的 Jant 备份，永远同时包含数据库和已上传媒体文件。**

## 什么才算完整备份

你必须同时备份：

- 数据库
- 媒体存储

如果你只备份数据库，你会保住 posts、collections、settings 和媒体元数据，但会丢掉真正的上传文件。

如果你只备份媒体存储，你会保住文件，但会丢掉指向这些文件的记录。

## Site Export 是干什么的

`site export` 是一个偏向可移植性的工具。

适合用在这些场景：

- 把内容迁移到另一个 Jant 站点
- 保留一个可移植归档
- 生成兼容 Zola 的静态导出

不要把 `site export` 当成生产环境灾难恢复的主要方案。

具体命令见 [导出与导入](export-and-import.md)。

## Site Snapshot 是干什么的

`site snapshot` 是一个偏向恢复的内容快照。

适合用在这些场景：

- 保留 post IDs 和存储键
- 在别处重建一份已知内容集
- 保留一个可以往返恢复的内容归档

Snapshots 比 `site export` 更接近恢复工具，但它依然不能替代完整的运维级备份方案。

## Cloudflare Workers

如果你在 Cloudflare 上运行 Jant，并使用 D1 + R2：

- 用你的 D1 恢复方式恢复数据库
- 媒体恢复要和数据库恢复分开考虑
- 只有在你的保留要求需要时，才额外增加平台外导出

对大多数小型站点来说，一个实用的方案通常是：

1. 近期数据库问题依赖 D1 恢复
2. 为 R2 或 S3 媒体制定明确的保留策略
3. 如果你想保留独立副本，就周期性做 export 或 snapshot

记住：对象存储的持久性，不等于你真的有恢复流程。

## Node 和 Docker

如果你使用默认的 Docker 或 Node 配置，请备份：

- `data/jant.sqlite`
- `data/media/`

如果你用的是 Postgres 而不是 SQLite，请备份：

- 你的 Postgres 数据库
- 如果你还在用本地媒体存储，也要备份本地媒体

如果你用的是 S3 兼容存储，而不是本地媒体存储，请备份：

- 数据库
- 媒体 bucket 以及它的保留策略

## 恢复检查清单

### Cloudflare 恢复

1. 恢复数据库
2. 如果涉及存储丢失，恢复缺失的媒体对象
3. 重新部署，或者让 Jant 指向恢复后的资源
4. 检查首页、collections、媒体 URL 和 settings

### Docker 或 Node 恢复

1. 停掉应用
2. 恢复数据库文件或数据库服务
3. 恢复媒体文件或媒体 bucket
4. 启动应用
5. 检查 posts、collections、uploads 和 feeds

## 恢复演练

在你真正需要恢复之前，先在一套空白的 staging 环境里做一次恢复演练。

清单：

1. 恢复数据库
2. 恢复媒体
3. 启动 Jant
4. 打开首页、settings，以及若干条样本帖子 URL
5. 检查附件和 collection 页面
6. 记录恢复花了多久，以及丢了多少数据

你至少要跟踪两个数字：

- **RPO**：你能接受丢失多少数据
- **RTO**：恢复最多能花多久

如果你连这两个数字都没法衡量，那你的备份方案就还没完成。

如果你不能有把握地把一份备份恢复到一套空白环境里，那你其实还没有一个真正的备份。
